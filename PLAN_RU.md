# План двух открытых репозиториев Tau — v0.1

## Принятые решения

1. Пользователь ведёт поиск, уточняет условия и получает результаты через чат с ИИ.
2. `tau-job-search-skills` задаёт метод исследования; `tau-job-scout` предоставляет ИИ локальные MCP-инструменты.
3. Scout работает на компьютере пользователя. Сервер, аккаунт и API Tau не нужны.
4. Пользователь подключает собственный `APIFY_TOKEN` в настройках окружения MCP-клиента. Токен не вводят в чат и не передают аргументом инструмента.
5. Первичная установка пакета и подключение MCP — отдельная настройка. В v0.1 не обещаем установщик в один клик или поддержку клиентов, умеющих подключаться только к удалённым MCP-серверам.
6. Модель уже работает в чате: она читает приложенное резюме, формирует профиль и объясняет рекомендации. Отдельный LLM API-ключ Scout не требуется.
7. В Apify отправляем роли, географию и фильтры. Резюме, имя, контакты и профиль кандидата туда не отправляем.

## Репозиторий Skills

Шесть независимо устанавливаемых skills:

| Skill | Результат в чате |
|---|---|
| `job-search-brief` | Профиль поиска из CV и явно заданных пожеланий |
| `linkedin-search-plan` | Поисковые запросы и согласованные ограничения |
| `job-research` | Запуск инструментов Scout или исследование доступными инструментами чата |
| `fit-review` | Совпадения, пробелы и неизвестные условия конкретной вакансии |
| `company-brief` | Справка о компании по доступным публичным источникам |
| `shortlist-review` | Приоритеты и следующие шаги по списку вакансий |

Структура: `skills/<name>/SKILL.md` и необходимые переносимые references внутри каждого skill; инструкции установки в `docs/`; синтетические примеры в `examples/`; проверки пакета и сценарии оценки в `checks/`. Общие материалы не должны быть обязательными внешними зависимостями отдельно установленного skill.

Берём из текущих ресурсов Tau метод поиска, brief, оценку соответствия и подход к источникам. Выбираем и редактируем, а не публикуем оба прежних пакета целиком. Skills работают и без Scout: через веб-инструменты чата или вставленные пользователем описания. Никаких обещаний свежих результатов без реально доступного источника.

## Репозиторий Scout

Python-пакет с официальным MCP SDK и транспортом stdio, локальной SQLite и одним поддерживаемым Apify Actor. Команда запуска сервера существует для MCP-клиента; команды поиска пользователь не вводит.

Основные модули: `server`, `config`, `models`, `storage`, `sources/apify`, `normalize`, `matching` и синтетические demo-данные. Точное фактическое дерево — в README; контракт инструментов — в `docs/tool-contract.md`.

| Инструмент | Назначение |
|---|---|
| `get_scout_status` | Наличие настройки токена и доступные возможности; без раскрытия секрета |
| `prepare_search` | Проверить и сохранить план поиска без платного запроса |
| `search_jobs` | Запустить один сбор для плана или вернуть уже существующий |
| `get_search_status` | Проверить существующий запуск и получить его результаты |
| `get_saved_results` | Вернуть сохранённые вакансии в чат |
| `rank_jobs` | Дать прозрачную базовую сортировку по профилю |
| `refine_shortlist` | Уточнить сохранённый список без нового платного сбора |
| `import_jobs` | Принять структурированные вакансии без доступа к файлам и сети |

Первая версия включает нормализацию, удаление дублей по ID/ссылке, историю локальных результатов, фильтрацию, объяснимый базовый ранг и демонстрационный поиск без токена. Глубокий разбор делает ИИ в чате. Вакансия, возвращённая сборщиком, считается обнаруженной, а не подтверждённо открытой сейчас.

## LinkedIn и Apify

Путь данных: **чат → локальный Scout → Apify API → Actor получает вакансии LinkedIn → Apify Dataset → Scout → чат**.

Первый адаптер: `bebity/linkedin-jobs-scraper`. По документации автора работает без LinkedIn-логина и cookies пользователя. Логин LinkedIn, браузер и профиль пользователя в Scout не подключаются. Apify — сторонний сборщик, а не официальное разрешение LinkedIn на scraping; доступность и полноту выдачи не гарантируем.

В отличие от Tau, Easy Apply — необязательный фильтр. Результаты с внешней формой подачи также нужны для исследования. Для каждого запуска задаём лимит результатов, стоимости и времени. Перед сбором чат сообщает источник и ограничения; отдельные подтверждения не нужны для каждого внутреннего шага в рамках уже запрошенного поиска.

План сохраняем до запуска. Повторный вызов с тем же планом не создаёт новый платный сбор. Если ответ на старт потерялся, показываем неопределённый статус и не пытаемся автоматически начать снова. Ошибка получения dataset повторяет чтение того же запуска, а не сбор. Новые условия сначала применяем к сохранённым вакансиям; дополнительный сбор запускаем только когда он нужен для запроса пользователя.

## Что остаётся в закрытом Tau

- Подключение LinkedIn, браузерные профили и управление сессиями.
- Easy Apply, движок ответов, заполнение форм и отправка заявок.
- Отправка outreach и последовательности сообщений.
- Автопилот, очереди, планировщик и управление несколькими клиентами.
- Производственные prompts, дополнительное ранжирование и оркестрация.
- Авторизация, биллинг, интерфейс, аналитика и инфраструктура Tau.

Открываем только выбранные инструкции, самостоятельную нормализацию, базовый matching и Apify-адаптер. Репозитории имеют новую Git-историю, MIT-лицензию и синтетические примеры. Персональные данные, окружение, ключи и продовые fixtures не переносятся.

## Этапы и приёмка

1. Зафиксировать контракт инструментов и форматы данных.
2. Параллельно реализовать Skills и рабочий Scout с demo/import.
3. Добавить асинхронный Apify-адаптер и проверки внешних границ без платных запусков.
4. Проверить MCP initialize/list/call через реальный stdio-транспорт; пройти поиск, чтение, ранжирование и уточнение.
5. Независимые подагенты проверяют Scout и Skills/интеграцию. Исправить подтверждённые замечания и повторить затронутые проверки.
6. Сохранить проверенный локальный результат в двух Git-репозиториях. Публикация на GitHub и загрузка пакетов — отдельный этап.

Первичная реализация была проверена без реальных токенов и платных запусков. После отдельного запроса пользователя выполнен ограниченный живой MCP-прогон; фактические результаты, исправления и ограничения — в [отчёте](docs/LIVE_TEST.md). Один успешный прогон не означает production-надёжность. Автоматизация LinkedIn-аккаунта не используется.
